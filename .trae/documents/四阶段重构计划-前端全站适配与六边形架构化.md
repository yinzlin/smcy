# 四阶段重构计划：前端全站适配 + 删除老系统 + 六边形架构化

## Context

用户确认三件事：① 全站页面做 PC/移动端全面适配；② 彻底删除老系统，全面使用重构后的架构；③ 严格按《Rust 全栈项目架构整合方案》（.trae/documents/）的六边形架构补齐业务逻辑层与用例层。

现状盘点证实了用户判断：
- **domain** 仅 308 行纯 serde DTO（方案要求：聚合根/值对象/出站端口/领域错误）
- **application** 仅 1587 行散装函数（excel 555 / price 391 / stock 361 / purchase 236 / order_no 25 / user 19），**无 dto/、port/、error/**
- **database** 仅连接池+迁移，**无仓储实现**；SQL 全部内联在 handlers.rs（**16031 行、249 个 api_ handler、17 处事务语句**）与 service 里
- **老系统** pages/mod.rs 13382 行服务端渲染旧页仍在（新前端已 1:1 覆盖全部 41 页并验证）
- **前端** 仅 MainLayout 响应式；157 处 `<Table>` 仅 9 处有 scroll.x；287 处固定宽样式；ItemsEditor 为 minWidth:1320 固定宽 WPS 键盘导航网格

硬约束：单 exe / Win7 / chrome87 构建目标；edition 2024 / resolver 3；**行为保持**——所有 API 响应体、状态码、中文错误信息逐字节兼容（前端 api 层零改动），此前 148 项冒烟为基线；依赖方向：domain 零外部依赖，application→domain(+common)，database→domain(+common)，backend→application+database，**domain/application 禁止依赖 sqlx**。

已确认决策：老系统**彻底删除**（git 历史可找回）；**分四阶段交付**，每阶段独立构建+冒烟+提交。

## 关键架构设计（阶段③④适用）

- **端口分发**：泛型注入（非 dyn/枚举）。Rust 2024 原生 async fn in trait 不可 dyn，但只有 SQLite 单实现，泛型单态化零开销、编译期检查。
- **事务边界下沉仓储实现**：17 处事务 handler 的多步 SQL 序列建模为聚合级仓储方法（如 `PurchaseOrderRepo::approve()`），实现内部 begin/commit，application 用例每次只调一个 repo 方法即天然原子。application 不碰 sqlx，符合六边形 Unit-of-Work 属于基础设施层的定位。
- **DTO 策略**：domain/lib.rs 现有请求结构**原位保留**（即 API 契约，避免 249 处引用爆炸）；新建 `application/src/dto/` 只放新抽取的响应结构，serde 字段名与现 json! 完全一致。
- **聚合与值对象**：随垂直切片逐步建立（如 PurchaseOrder 聚合承载 can_approve/can_unapprove/结算状态机与金额校验规则），不为建模而建模。
- **di.rs**：手动构造 `App { 各用例字段 }`，handler 从 `State<App>` 取用例；`database::pool()` 全局访问最终仅剩 di.rs 一处。

## 阶段① 前端全站 PC/移动全面适配

**新建 3 个共享件**：
- `crates/frontend/src/hooks/useIsMobile.ts` — 抽取 MainLayout 模式（`Grid.useBreakpoint()`，`screens.md === false`）
- `crates/frontend/src/utils/tableScroll.ts` — `calcTableScroll(columns, extra?)` 按 Σ(column.width ?? 120) 计算 scroll.x
- `crates/frontend/src/styles/mobile.css`（main.tsx 引入）— `.ant-modal{max-width:calc(100vw - 16px)}`（calc/vw 均在 chrome87 支持范围内）

**逐类改动**：
1. 全站列表/查询页 Table 补 `scroll={calcTableScroll(columns)}`（约 35 文件：query/ 24 页、admin/ 管理页、product、priceschedule、todayprice 等）
2. **ItemsEditor 移动端卡片式明细**（`pages/sales/ItemsEditor.tsx`、`pages/purchase/ItemsEditor.tsx`）：`useIsMobile()` 为真时不渲染 `<table>`，改 div 卡片（商品联想→单位→单价/数量/金额纵排→删除）；`focusCell/handleEnterNav` 仅桌面分支执行；数据/校验/取价逻辑（applyProduct、scheduleUnitPrice）完全复用。桌面布局不动
3. FormCard 顶部字段改响应式 Row/Col（`xs={24} sm={12} lg={8}`）：SalesFormCard、PurchaseFormCard、ProductEditModal、CreateProductCard、PriceSchedulePage 弹窗、OrderAdjustPage 弹窗（约 8 文件）
4. 统计条/合计行 Col span 响应式（约 15 文件，随 scroll 改动一并做）
5. LoginPage 卡片 `width:'100%', maxWidth:400`；HomePage 已响应式不动

**验证**：tsc 零错误 + npm build；浏览器 390px 宽抽查：/login、/、/supplier、/product、/purchase、/sales、/today-price、/price-schedule、/query/stock-balance、/query/sales-order、/query/order-adjust、/supplement、/user、/backup、/mobile/sort——无页面级横向滚动（表格容器内滚动除外）、Modal 不超视口、PC 端布局无变化。

## 阶段② 彻底删除老系统

- 删 `crates/backend/src/pages/mod.rs` 整文件；main.rs 去 `pub mod pages`
- routes.rs：删 `use crate::pages::*`、全部 `/legacy/*` 路由、`page_*` 引用；**保留** redirect_app! 宏的 `/xxx`→`/app/xxx` 302（书签兼容）、`/`→`/app`、`/login`→`/app/login`
- 删 `crates/backend/src/static_assets.rs` 与 `crates/backend/static/`（bootstrap/chart.js 仅老页用，前端无引用）及 `/static/*` 路由
- MainLayout.tsx 删「老系统入口」按钮
- app_assets.rs 重定向函数全部保留（老 URL 归宿），仅更新注释；tray.rs 打开 `http://127.0.0.1/` 经重定向即达，不动；**/api/* 全部保留**

**验证**：cargo build + 冒烟：`/`→302|307→/app、`/login`→302|307→/app/login、`/legacy/login`→404、`/app` 200、`/api/login` 200、全套 API 冒烟绿；exe 体积明显缩小。**本阶段单独成 commit**（revert 即恢复老系统）。

## 阶段③ 六边形化核心写域（垂直切片，每片独立提交+冒烟）

**新建结构**：
- `domain/src/port/`：user.rs（UserRepo）、basic.rs（SupplierRepo/PurchaserRepo/ProductRepo/CategoryRepo/WarehouseRepo/ProductUnitRepo/ProductPriceRepo/PurchaseDocumentRepo）、price.rs（PriceScheduleRepo）、inventory.rs（InventoryRepo）、purchase.rs（PurchaseOrderRepo）、sales.rs（SalesOrderRepo）、supplement.rs、system.rs（SystemConfigRepo/BackupRepo/OperationLogRepo）；`domain/src/error.rs` 领域错误
- `application/src/port/`（入站 UseCase trait，文档要求）、`application/src/dto/`、`application/src/error.rs`
- `application/src/service/` 重构为用例编排（如 `ApprovePurchaseOrder<R: PurchaseOrderRepo>`）
- `database/src/sqlite/repo/`：按域一个文件实现端口，SQL 从 handlers **逐字搬运**，事务方法内部 begin/commit
- di.rs 扩展 App 结构装配

**切片顺序**（依赖序）：user/auth → category/warehouse → supplier/purchaser → product(+unit/price) → price_schedule → inventory → purchase_order（含 4 个事务 handler：update/approve/unapprove）→ sales_order（含 update/settle/approve/unapprove 4 个事务 handler）→ supplement/allocation。现有 service/price.rs、stock.rs 函数体迁入对应 repo 实现。

**handler 瘦身后只做**：check_api_permission → get_user_ctx → 组命令 → 调用用例 → 错误映射（中文文案逐字节照抄）。

**验证**：每切片仓库根 `cargo check` + `scripts/smoke.ps1 -Quick`（写域）；事务 handler（approve/settle/反审核）另做前后状态比对。

## 阶段④ 查询域与系统域收尾

- 46 个 `api_query_*` 只读接口（25 查询+21 导出）→ `application/service/query/`（purchase/sales/stock/finance/report 5 文件）+ `database/src/sqlite/repo/query/`；动态拼接 SQL 逻辑逐字迁移（注意列名歧义教训）
- 导出接口 = query 用例取行 + service/excel.rs 组装（excel.rs 保留）
- 系统域：config/backup/restore/operation_log/inspect_corrupted/clean_invalid_orders → system 用例+仓储
- 收尾：main.rs 删兼容 shim（`pub(crate) use domain as models` 等）、handlers.rs 残留 SQL 清零、`database::pool()` 仅 di.rs 引用、依赖矩阵复核（application 无 sqlx）
