# 前端技术栈对比与 React 迁移评估

> 项目：smcy（食堂验收管理系统）
> 日期：2026-10-14
> 范围：前端 UI 层现状、与 React 工程化栈的对比、迁移成本评估

---

## 一、现状技术栈

当前前端**没有使用**任何现代前端框架，是"Rust 后端直出 HTML + 原生 JS"的单体架构。

| 层 | 当前实现 | 说明 |
|---|---|---|
| 视图 | 原生 JavaScript 字符串拼接 HTML → `innerHTML` | 无模板引擎、无 JSX、无虚拟 DOM |
| 构建 | 无（无 `package.json`、无 `node_modules`、无打包器） | HTML/CSS/JS 全部内嵌在 Rust 源码字符串中 |
| 路由 | 自实现 hash 路由 | `#/path` → 页面渲染函数映射 |
| 状态 | 全局变量 + `localStorage` | 无统一状态管理 |
| 异步 | 原生 `fetch()` | 无请求库、无缓存/去重/自动刷新 |
| 组件库 | Bootstrap 5（本地引入） | 弹窗/表格/表单样式 |
| 图表 | Chart.js（`/static/chart.umd.min.js` 本地引入） | 价格趋势折线图 |
| 样式 | Bootstrap 类 + 内联 `<style>` | 无 CSS 预处理器、无原子化 CSS |

### 代码规模实测

|---|---|---|

## 二、与 React 工程化栈逐项对比

| 能力 | React 技术栈（图示） | 当前项目 | 差距 |
|---|---|---|---|
| 视图 | JSX（React） | 原生 JS 拼字符串 | 无组件化、无类型检查、无复用 |
| 构建 | Vite | 无构建 | 无热更新、无压缩、无 TS |
| 路由 | React Router | 自实现 hash 路由 | 功能等价，但无嵌套路由/守卫/懒加载 |
| 状态 | Zustand / Redux | 全局变量 + localStorage | 状态散落，跨页共享靠手动同步 |
| 异步 | TanStack Query | 裸 fetch | 无缓存、无 loading/错误统一处理、无自动重取 |
| 组件库 | AntD | Bootstrap 5 | AntD 表格/表单/日期等组件能力远强 |
| 样式 | Tailwind | Bootstrap 类 + 内联样式 | 无设计令牌、样式复用靠复制 |

## 三、迁移到 React 栈的成本评估

### 3.1 工作量构成

| 工作项 | 说明 | 估算 |
|---|---|---|
| 工程初始化 | Vite + React + TS + 路由 + 状态 + 请求层 + AntD 接入 | 1~2 天 |
| **页面重写** | 510 个 JS 函数、14k 行逻辑拆成 React 组件 | **大头** |
| API 层对接 | 200 处 fetch 收敛为统一 client + React Query hooks | 3~5 天 |
| 路由迁移 | hash 路由 → React Router（含权限/守卫） | 1 天 |
| 状态迁移 | localStorage + 全局变量 → Zustand store | 2~3 天 |
| 样式迁移 | Bootstrap → AntD + Tailwind 重写布局 | 3~5 天 |
| Excel 导出 | 导出逻辑在 Rust 后端（`build_accept_excel`），**不受影响** | 0 |
| 联调回归 | 257 个 API 全链路验证 | 3~5 天 |

### 3.2 页面重写是主要成本

14,042 行前端代码，按功能模块粗分（按函数名/页面名统计）：

| 模块 | 预估页面数 | 复杂度 | 估算 |
|---|---|---|---|
| 商品/分类/供应商/采购单位管理 | ~12 | 低（CRUD + 弹窗） | 3~4 天 |
| 采购订单/销售订单/验收单 | ~8 | **高**（多行明细、比价面板、单位换算、价格联动） | 5~7 天 |
| 今日进价采集 | ~2 | 中（卡片列表 + 保存） | 1~2 天 |
| 价格策略/价格趋势 | ~4 | 中（表格 + 折线图） | 2~3 天 |
| 报表/查询/导出 | ~6 | 中（筛选 + 表格） | 2~3 天 |
| 库存/仓库/调拨 | ~4 | 中 | 2~3 天 |
| 其他（登录、设置、导入） | ~6 | 低 | 1~2 天 |

**页面重写合计：约 16~24 天**（1 人全栈，含测试）

### 3.3 总成本估算

| 方案 | 范围 | 总工作量 |
|---|---|---|
| **整体重写** | 全部 42+ 页面迁到 React | **约 25~35 天**（5~7 周） |
| 渐进迁移 | 后端不变，先迁高频/复杂页面（订单、采集、价格），其余保留原生 JS | 12~18 天 |
| 仅加构建工具 | 不迁框架，只把 14k 行 JS 从 Rust 字符串抽出为独立文件 + ES Module | 2~3 天 |

## 四、迁移的收益与代价

### 收益

- **可维护性**：组件化后，比价面板、单位换算等复杂交互不再嵌在 14k 行单文件里
- **类型安全**：TS + API 类型生成，减少 `form.xxx.value` 这类运行时崩溃（如之前 `gov_status` 的新增表单 bug）
- **开发效率**：Vite 热更新，改前端不用重编译 Rust（当前改一行 JS 需 `cargo build` 约 45s）
- **UI 能力**：AntD 表格（虚拟滚动、列配置、导出）、表单校验、日期范围选择等开箱即用

### 代价与风险

- **部署形态改变**：当前单 exe 直出 HTML，React 需构建产物。可选方案：
  - 后端仍用 `rust-embed`/`include_dir` 把 `dist/` 打包进 exe → 保持单文件部署（推荐，契合 Win7 单机）
  - 或前后端分离部署 → 需额外 Web 服务器
- **构建依赖**：需 Node.js 环境构建（部署机不需要，开发机需要）
- **回归风险**：42+ 页面重写必然引入行为差异，需充分回归测试（尤其订单金额、单位换算、导出这些强正确性场景）
- **学习成本**：若后续维护者不熟 React/TS，反而增加负担

## 五、建议

| 场景 | 建议 |
|---|---|
| 系统稳定运行、功能不再大改 | **不迁移**。当前架构零依赖、单 exe、Win7 兼容，维护成本可控 |
| 前端还要持续加复杂功能（多级审批、看板、移动端） | **渐进迁移**：后端 API 不动，新页面用 React 写，老页面逐步替换 |
| 当前最大痛点是"改 JS 要重编译 Rust" | **先做轻量改造**（方案三）：把 JS 抽出为独立静态文件，引入 Vite 只做打包不做框架迁移，2~3 天见效 |

**结论**：当前项目不建议整体迁移到 React。若确需现代化，推荐"渐进迁移"或"先抽离构建"两步走，避免一次性重写 42+ 页面带来的回归风险和 5~7 周停工。
