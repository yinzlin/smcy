# 迁移指南：从旧结构平滑过渡到六边形脚手架

**版本**: v1.0   **日期**: 2026-10-16   **配套文档**: [Rust 全栈项目架构整合方案.md](./Rust%20全栈项目架构整合方案.md)（目标态）、[六边形分层规则.md](./六边形分层规则.md)（ADR）

本指南以本仓库的真实迁移路径为蓝本，说明如何把一个**单 crate 巨石 + 服务端渲染**的旧项目平滑迁移到**严格六边形 workspace + 内嵌 React SPA** 的脚手架目标态。全程可上线、可回退、行为零变更。

---

## 一、起点与终点

| | 旧结构（起点） | 新结构（终点） |
| --- | --- | --- |
| 后端 | 单 crate：`src/main.rs`（路由 + Excel + 托盘）、`api/mod.rs`（全部 handler）、`pages/mod.rs`（SSR 页面）、`db.rs`、`auth.rs`、`utils.rs`、`models.rs` | cargo workspace 5 crate：common / domain / application / database / backend |
| 前端 | 服务端渲染 HTML + 原生 JS + Bootstrap（内嵌字符串） | React 18 + AntD 5 SPA，rust-embed 内嵌挂 `/app` |
| 依赖规则 | 任意互调（api 反调 main、handler 直连 pool） | 5 条分层硬约束，脚本护栏站岗 |
| 交付 | 单 exe（已具备 Win7 兼容） | 单 exe 不变，前端产物编译期内嵌 |

**迁移铁律**：先立规则（ADR），再机械搬迁，再逐层去穿透，最后动前端。任何一步行为变更都必须能被冒烟基线捕获。

---

## 二、迁移前准备（阶段零）

1. **建立行为基线**：编写冒烟脚本覆盖全部关键接口（本仓库基线为 `scripts/smoke.ps1` 232 条断言），在**隔离目录**运行（如 `%TEMP%\xxx_smoke`），避免依赖本机数据库状态。没有基线不动工。
2. **定稿 ADR**：先把目标分层规则写成判定标准（依赖白名单、pool 唯一路径、契约归属、错误映射链、接口兼容红线），作为后续每刀的对错判据。
3. **分支策略**：`main` 保持可发布；后端拆分在 `refactor/*` 分支一次到位（机械搬迁便于 diff 审查）；前端每页一支 `feature/*`。
4. **备份产物**：保留旧 exe 与数据库备份，阶段一可整体 `git revert`。

---

## 三、阶段一：后端 workspace 拆分（纯搬迁，无行为变更）

目标：代码位置变化，行为逐字节不变，随时可上线。

### 3.1 建骨架

- 根 `Cargo.toml` 改 `[workspace]`（`resolver = "3"`），声明 5 个 crate 成员与 `workspace.dependencies`；版本与 features 与原单 crate 保持一致。
- `rust-toolchain.toml` 固定 nightly 日期，防工具链漂移。
- `.cargo/config.toml`（win7 target / build-std / crt-static）原样保留。
- 暂不用的目录按需留空占位即可，**不必为同构而同构**（后续 ADR 已明确不恢复模板空目录）。

### 3.2 代码搬迁映射

| 旧位置 | 新位置 | 备注 |
| --- | --- | --- |
| `src/models.rs` | `domain/src/lib.rs` | 纯结构体原样迁入 |
| `src/utils.rs` | `common/src/utils/` | 托盘相关函数移到 backend（common 不带桌面依赖） |
| `src/db.rs` | `database/src/lib.rs` + `sqlite/mod.rs` | 连接池、建表、损坏修复 |
| `src/auth.rs` | `backend/src/middleware/auth.rs` | 会话检查 + 路由权限映射 |
| `src/api/mod.rs` | `backend/src/api/handlers.rs` | 全部 handler 原样迁入，仅改引用路径 |
| `src/pages/mod.rs` | `backend/src/pages/` | 老 SSR 页面原样保留 |
| `main.rs` 路由表 | `backend/src/api/routes.rs` | 路由条数逐条不变 |
| `main.rs` 的 `fn main()` + 托盘 | `backend/src/main.rs` | EventLoop + TrayIcon 保留 |
| `main.rs` 中被 api 反调的业务函数 | `application/src/service/*.rs` | 消除 main↔api 反向调用 |

### 3.3 批量引用替换

```
crate::db::pool()   → database::pool()        （全局替换，数百处）
crate::models::     → domain::
crate::utils::      → common::utils::
crate::<业务函数>    → application::service::<模块>
```

### 3.4 循环依赖处理

若 `db.rs` 的启动迁移逻辑需要回调业务函数（如重建价格时段），直接回调会形成 `database → application` 反向依赖。解法：**database 迁移函数只返回"待修复项列表"，由组合根（`backend/src/di.rs`）启动时补调 application 服务**。

### 3.5 阶段一验收

1. `cargo check` workspace 全绿后**才删除**旧 `src/`；
2. win7 target release 构建产出演示 exe；
3. 冒烟基线全通过（路由数、cookie 会话、托盘行为不变）。

## 四、阶段二：六边形严格化（去穿透）

搬迁完成后骨架已立但穿透仍在（application 裸 SQL、中间件直连 pool、`*Req` 落 domain）。按 Phase 1→4 收敛，**每 Phase 独立提交，每步 cargo check + 冒烟全绿**。

### Phase 1：中间件端口化（先做，闭环样板）

1. 审计中间件裸 SQL（如 auth.rs 的取角色、写日志）；
2. 在 `domain/src/port/` 对应端口补方法签名（如 `UserRepo::session_ctx`），`database` 实现；
3. 中间件函数签名改为接收 repo 参数，删除 `use sqlx::Row` / `use database::pool`；
4. `di.rs`：**同一 repo 实例**既注入 service 也挂为 `App` 字段（供中间件经 `State<App>` 取用）；
5. handlers 中所有中间件调用点机械补参（本仓库约 100 处）。

> 样板意义：这一刀跑通「端口补方法 → 实现 → 注入 → 调用点改造」全流程，后续 Phase 都是它的重复。

### Phase 2：application 去穿透（工作量主体）

按「先删重复、再补新口」两步走：

- **删重复**：大量裸 SQL 是「端口已实现、旧函数未删」的重复实现——删除旧函数，调用点改为经注入的 repo（`self.repo.*`）。
- **补新口**：无现成端口者，在 `domain/src/port/` 对应 trait 加方法、database 实现（如单号生成的 `max_seq_for_date`）。
- **收依赖**：从 `application/Cargo.toml` 移除 `database` 与 `sqlx`，清理 `use database::*` / `use sqlx::*`。

完成标志：`grep "pool()|sqlx::" crates/application/src` 零命中。

### Phase 3：`*Req` 契约迁移

1. 全部 `*Req` 从 `domain` 移入 `application/src/dto/`，**derive、`#[serde(default)]`、字段名与顺序逐字保留**（serde 序列化顺序 = 字段声明顺序，动了就破契约）；
2. domain 端口若以 `*Req` 为出入参，因 domain 不得依赖 application，需在 **domain 侧建同名同序的 Input 结构体**（不派生 `Deserialize`），application 收参时 `From<Req> for Input` 映射；
3. handlers 的 `use domain::*` 收口为对 `application::dto::*Req` 的精确导入；
4. `UserCtx` 留在 domain——它是共享会话上下文的领域概念，非 HTTP 契约。

### Phase 4：护栏固化

把 ADR 固化为可执行脚本（本仓库 `scripts/check_layers.ps1`，5 条断言：domain 仅 serde / application 无 pool+sqlx / domain 无 *Req / 非 di.rs 无 pool / application Cargo.toml 无 db 依赖），挂 `make check-layers`，并固化为项目 Skill 长期站岗。**没有护栏的架构会再次漂移。**

## 五、阶段三：前端 React 迁移（逐页，老页共存可回退）

1. **脚手架**：`crates/frontend/`（npm 工程，workspace `exclude`），Vite 5 + React 18 + TS + AntD 5 + react-router 6 + zustand；构建目标 `chrome87`（兼容 Win7 的 Chrome 109）。
2. **嵌入共存**：backend 用 rust-embed 内嵌 `dist` 挂 `/app`（SPA 无扩展名回退 index.html）；老页面路由原样保留，**每迁完一页，老路由 302 跳新页，旧页留 `/legacy/*` 回退**；单 exe 形态不变。
3. **鉴权复用**：同源 fetch 自动带 HttpOnly cookie，会话存 zustand，权限点镜像后端判定。
4. **迁移顺序**：登录页 → 主布局（菜单/权限）→ 核心页逐页推进，**每页独立 PR**，与老页面并排核对数据 / 金额 / 单位换算一致。
5. **移动页**：全屏独立路由（不挂主布局），用 `Grid.useBreakpoint` 的 `screens.md === false` 判定移动端，避免 PC 首帧闪移动布局。
6. **实测**：Chrome 109（Win7 上限）逐页验证。

## 六、代码去向决策树

迁移中任何一段代码按此归位：

```
这段代码做什么？
├─ 执行 SQL / 查询          → database/src/sqlite/repo/<域>.rs
├─ 纯业务规则 / 编排用例     → application/src/service/<域>.rs（经端口取数，禁止裸 SQL）
├─ HTTP 请求体结构 (*Req)    → application/src/dto/<域>.rs
├─ 仓储/外部能力接口 (trait) → domain/src/port/<域>.rs（出入参用 domain 自有类型）
├─ 领域错误 / 会话上下文     → domain/src/error.rs、domain/src/lib.rs（UserCtx）
├─ 路由 / handler / 中间件
│  / 托盘 / 静态资源         → backend/src/（pool 只允许在 di.rs 出现）
└─ 无业务语义的通用纯函数    → common/src/utils/
```

拿不准时的判据：**删掉它，谁最受影响**——只影响 HTTP 形态的归 backend，换数据库就要改的归 database，两者都不变的归核心层。

## 七、常见陷阱与对策

| 陷阱 | 对策 |
| --- | --- |
| 搬迁后 `crate::` 残留编译错 | `cargo check` 全绿前不删旧 `src/` |
| nightly 工具链漂移导致构建失败 | `rust-toolchain.toml` 锁定 |
| database 回调业务形成循环依赖 | 迁移函数返回"待办列表"，di.rs 启动补调 |
| serde 字段顺序变动破坏前端契约 | `*Req` 逐字迁移；冒烟基线兜底 |
| `Redirect::temporary` 实际返回 307 而非 302 | 冒烟断言接受 `302\|307` |
| 冒烟依赖本机数据库/密码哈希 | 隔离目录运行 + 种子库可重置（如 `PUT /api/user/1`） |
| React 迁移回归 | 每页独立 PR + `/legacy/*` 回退 + DB schema 全程不变 |
| 组件渲染期引用靠后声明的 const 箭头函数 | TDZ 运行时错误且 tsc 检不出——纯函数提到组件外模块作用域 |
|  antd `DatePicker` 无 `valueFormat` prop | 统一 `onChange` 内 `d.format('YYYY-MM-DD')` |
| 迁移中途想"顺手优化"业务逻辑 | 禁止。迁移只搬家，优化另起提交，否则回归无法归因 |

| 阶段 | 必过项 |

## 九、迁移节奏总览

```
阶段零  行为基线 + ADR + 分支策略
阶段一  建骨架 → 机械搬迁 → 引用替换 → 循环依赖处理 → 验收删旧
阶段二  Phase1 中间件端口化 → Phase2 去穿透 → Phase3 *Req 迁移 → Phase4 护栏
阶段三  前端脚手架 → 嵌入共存 → 逐页迁移（登录→布局→核心页→移动页）→ 收尾
```

全程主线只有一条：**每一步都可构建、可冒烟、可回退**。做到这点，迁移没有"大爆炸"时刻。
